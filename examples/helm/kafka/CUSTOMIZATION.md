## External dependency analysis

**Kafka IS the service — there are no bundled dependencies to replace.**

Unlike charts such as Bitnami Redis (which bundles a Sentinel/Replica subchart) or
application charts (which bundle PostgreSQL), the Bitnami Kafka chart in KRaft mode
ships no external-service subcharts. Specifically:

- **Zookeeper**: chart 32.x defaults to KRaft (no Zookeeper); `zookeeper.enabled`
  is absent from the default values — the ZK dependency was removed upstream.
- **Schema Registry / Kafka Connect / REST Proxy**: not bundled; these are separate
  Bitnami charts (`bitnami/schema-registry`, `bitnami/kafka-connect`). If the ISV
  wants to offer them, add them as sibling services with `dependsOn: Kafka Cluster`.
- **Object storage for tiered storage**: Kafka 4.x supports remote/tiered storage;
  the Bitnami chart does not configure it by default. If the ISV adds tiered storage
  to a later phase, the appropriate pattern is a terraform-managed S3 bucket wired
  via `{{ $tfService.out.<key> }}` (see HELM_ONBOARDING_REFERENCE.md §External dependencies).

**Verdict**: no replacement suggestion. The chart self-contained; default Tier-2 values
(SASL credentials for interbroker/controller, persistence PVCs) are the ISV's operational
responsibility — no managed cloud service substitution is needed or recommended for MVP.
