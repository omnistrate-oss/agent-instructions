## External dependency analysis

### PostgreSQL IS the data service

The Bitnami PostgreSQL chart deploys PostgreSQL directly — PostgreSQL is not a
subchart dependency here. It is the primary workload. There is no bundled external
data store to replace.

The chart has one dependency declared in Chart.yaml:
- `common` (bitnami common library) — a helper chart with templates/helpers only;
  it creates no Kubernetes workloads or data stores. This is not an external
  data dependency.

**Conclusion:** No subchart data dependency to replace via Terraform.

### S3 for backups — analysis per guide

HELM_ONBOARDING_REFERENCE.md §"External dependencies" states:
> "Option B (suggested for production tiers): replace it with a terraform-managed
> cloud service — RDS for PostgreSQL/MySQL, ElastiCache for Redis/Memcached, **S3 for
> object storage**."

The Bitnami PostgreSQL chart v18.8.0 does **not** natively configure S3 backup
integration in its values (no `backup.s3.*` or similar block in the chart surface
examined). WAL archiving and pgBackRest/barman-based backup would require a
separate sidecar or init-container not bundled in the chart at this version.

**Recommendation for backups (BYOC context):**
- For the Dev tier: rely on PVC-based point-in-time recovery (chart default).
- For production BYOC: provision a customer-account S3 bucket via a sibling Terraform
  service, wire the bucket ARN into a pgBackRest or WAL-G sidecar configuration as
  an extended value block. This is beyond the chart's native values surface.

**Gap note:** The guide's external-dependency section covers S3 for object storage in
general but does not provide a PostgreSQL-specific backup sidecar pattern. Implementing
S3 backup with the Bitnami chart requires custom Terraform + sidecar configuration
not covered by the current skill references.
